# Application review — 2026-11-01

The review covered the Spring Boot API/services/persistence, authentication and settings,
YouTube requests, recommendation/discovery/summary flows, Python NLP and transcript
service, frontend state handling, and Docker Compose configuration. Existing feature
work and Dockerfile changes were retained. No live database migration or deployment
was performed.

## Corrections

- **YouTube identity and query handling:** encode parameter values once, preserving
  `+`, `&`, percent characters and Unicode. Resolve complete Unicode/encoded handles;
  reject URLs on unrelated hosts and missing explicit handles rather than silently
  selecting a namesake. Store canonical creator-channel URLs. Request-failure messages
  no longer expose the underlying URL that could contain an API key.
- **Current retrieval settings:** each ingestion returns the video and comment IDs
  actually fetched. Recommendation evidence uses those records, so reducing a video
  or comment limit, changing the date window, or receiving no current uploads does
  not reuse older stored evidence. Historical associations remain stored on old runs.
- **Comment refresh:** update edited text, publication metadata and likes on existing
  comments without duplicating them. Both creator and competitor ingestion follow
  the same behavior.
- **Deletion:** explicitly delete comments and videos before deleting/replacing their
  channel. This works on both the SQL schema and databases generated by Hibernate,
  where scalar ID fields do not automatically create cascading foreign keys.
- **Concurrent writes:** lock the user's existing row for run creation and channel
  additions/configuration. Concurrent generation requests cannot both pass the
  active-run check; competitor/channel additions are serialized for the same user.
- **Frontend generation:** schedule the next progress read after the previous read
  completes. Closing Settings cannot enable generation during an active run. Retry
  interrupted progress reads without overlapping requests or repeated error toasts;
  handle missing runs and authentication failures. Disable duplicate suggested-channel
  additions across all three suggestion panels while a request is pending.
- **Transcript outcomes:** select regional variants such as `en-GB` for an English
  preference. An empty caption body is a retrieval error rather than evidence that
  subtitles do not exist. Manual/automatic selection and the exact absence message
  remain supported.
- **Discovery input budgets:** check actual serialized JSON lengths, including
  escaping and verification metadata. Fit complete video records and split candidate
  verification into bounded batches. Fail clearly for an unusably small configured
  prompt limit. Allow unknown optional generated IDs/URLs to be omitted or null.
- **Validation:** reject duplicate keys in model JSON; return HTTP 400 for malformed
  JSON/type parameters; validate resulting settings when only the retrieval mode
  changes. Bound signup names/emails and BCrypt password inputs before storage.
  Unexpected server failures return a generic message rather than internal details.
- **Existing NLP correctness:** preserve comment/like-count alignment when filtering
  blank comments. Fit the existing TF-IDF fallback vocabulary per analysis batch,
  rather than retaining the first request's vocabulary for all later requests.
  Handle empty fallback vocabularies without crashing. The sentence-transformer,
  topic, sentiment, intent and demand algorithms are preserved; no models or
  infrastructure were introduced.

The project's existing `.venv` was missing `youtube-transcript-api`; version 1.2.4 and
its missing XML-parser dependency were installed. `pip check` reports no broken
requirements. Runtime startup was checked using the existing cached sentence-transformer
backend with model downloads disabled.

## Verification

- 47 Java tests, including real HTTP clients and H2 persistence with fake external
  YouTube/LLM/transcript providers; concurrency, source windows, comment refresh,
  cleanup, request encoding, ownership, validation, budgets and summary caching.
- 35 Python tests, including the existing NLP tests and regressions for independent
  TF-IDF batches, blank-comment weights, caption variants and empty caption bodies.
- 8 frontend DOM tests, including slow polling and generation controls during a run.
- Executable Spring Boot JAR packaging under Java 17; verified launcher manifest and bundled dependencies.
- JavaScript syntax checks, Windows-line-ending-aware Git whitespace check, and
  `docker compose config --quiet`.
- Actual Python service startup, HTTP health, transcript route registration, and
  HTTP demand analysis using the project's existing virtual environment. The
  temporary smoke-test server was shut down after verification.

Live YouTube quota, live subtitle accessibility, LLM provider behavior and full Docker
image rebuilds were not established by these deterministic tests.

## Subsequent local startup, UI and documentation

After the review above, the five local Compose services were started on Linux Mint.
The current JAR and Python application were used with the existing dependencies and
cached model; this was not a clean rebuild of every full image. Existing database and
model volumes were preserved. Frontend pages and `/api/health` returned HTTP 200 through
http://localhost:8081, and Python health also passed.

The UI refresh retained the existing endpoints/components and added a split auth page,
creator workspace styling, verified suggestion cards, numbered idea cards, expandable
details and styled transcript panels. All eight DOM workflow tests passed again after
the refresh, along with JavaScript syntax, whitespace and live page checks. Browser
visual review was unavailable. These checks do not establish live SMTP delivery.

All ten project Markdown guides were refreshed to reflect implemented features, API
routes, persistence, test coverage, startup status and email limits. Generated pytest
cache documentation was excluded. The [email guide](email-notifications-implementation.md)
and its [Word copy](Email_Notifications_Implementation_Guide.docx) cover SMTP setup and
controlled verification.

A read-only remote check confirmed that local Git SSH access works. The repository was
also reachable through GitHub's unauthenticated API as public. The Azure Terraform files
use AzureRM/random providers and a credential-free HTTPS `repo_url`, so this deployment
needs no GitHub PAT. No token was collected, no mail was sent and no Terraform apply was
performed for these follow-up changes. See [authentication details](../AZURE_TERRAFORM.md#21-authentication-and-github-tokens).
